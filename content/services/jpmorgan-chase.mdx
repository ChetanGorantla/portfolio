## In short

I doubled Cassandra read throughput on a 10M-record dataset, and moved 100+ GB of legacy Cassandra data to S3 as Parquet with a pipeline that can fail partway and pick up where it left off.

## The problem

A dashboard queried customer trade data slowly, without using what Cassandra is good at. Separately, the company was migrating internal services to AWS to invest in cloud infrastructure.

## What I built

- **Query-shaped tables:** row widths matched to the query patterns, plus denormalized tables so each common query reads from a table built for it
- **Fewer network hops:** prepared statements and token-aware routing, so requests go straight to a node that owns the data
- **The migration:** a Java thread-pool pipeline of concurrent multipart uploads to S3

## The hard part

At 100+ GB, something breaks partway through. **Checkpointed retries** resume from the last good point, **idempotent writes** make a retried chunk safe, and **tuned backpressure** keeps the pool from reading faster than it can upload.

## What I learned

Cassandra rewards designing tables around your reads, and that's the reason to choose it over other NoSQL stores. Batch jobs need precise failure handling and rollbacks. Next time I'd add a watchdog that observes running batches instead of waiting for status reports.
