## Summary

Two jobs on the same data. I doubled Cassandra read throughput on a 10M-record dataset by reshaping the data model around its query patterns. I also migrated 100+ GB of legacy Cassandra data to S3 as Parquet, with a concurrent Java pipeline that can fail partway and pick up where it left off.

## Context

> Customer trade data was queried slowly in a dashboard, not making use of Cassandra's tradeoffs. The company also wanted to perform an internal service migration to AWS to invest in cloud infra.

## Approach

**Reads.** Cassandra rewards tables designed around the queries you actually run. I:

- redesigned row width to match the query patterns,
- built denormalized query tables, so each common query reads from a table shaped for it,
- cut network hops with prepared statements and token-aware routing, so requests go straight to a node that owns the data.

**Migration.** The 100+ GB move to S3 as Parquet ran through a Java thread-pool pipeline of concurrent multipart uploads.

## The hard part

Making the migration safe to fail. At 100+ GB, something will break partway through, and starting over from zero isn't a plan. I hardened the pipeline with:

- **checkpointed retries**, so a failure resumes from the last good checkpoint,
- **idempotent writes**, so retrying a chunk is safe to repeat,
- **backpressure tuning**, so the thread pool doesn't read faster than it can upload.

## Resolution

- Cassandra read throughput on 10M records went from **1× to 2×**.
- 100+ GB of legacy Cassandra data migrated to S3 as Parquet.
- The migration pipeline retries idempotently from checkpoints, with tuned backpressure.

## Lessons learned

> Read-side optimization is the key differentiator between using Cassandra vs other NoSQL databases. It's important to configure the database as optimally as possible to support fast reads, since that's one of the core motivations behind Cassandra. Also, batching needs precise failure handling and rollbacks to ensure data recovery.

## If I did it again

> I would maintain a watchdog that can observe the status of a batch job rather than waiting for status reports. This would introduce more overhead of a persistent connection, but would allow engineers the organization of tracking currently-running processes.
